## User reply: Brave (Android). Diagnosis detail (pdfjs v6.2.108)
- pdfjs v6 creates the worker via `new Worker(t, {type:"module"})`. If workerSrc is same-origin, it loads directly; otherwise it wraps with `await import("${url}")` in a Blob. pdfImport.ts sets workerSrc via `import("pdfjs-dist/build/pdf.worker.min.mjs?url")` — a Vite ?url import returning a full http URL in same origin, so module worker should work in Chromium. BUT Brave Android may block cross-site workers or the user's Brave shields block it; also `GlobalWorkerOptions.workerSrc` in pdfjs v6 must be set BEFORE getDocument.
- Safer approach: disable the module worker on mobile and use the built-in fake/main-thread setup OR provide a CDN fallback URL. pdfjs v6 no longer ships a legacy non-module worker build (no pdf.worker.min.js in v6 build dir).
- Best robust fix: keep module worker as primary; if worker setup fails, catch and use `disableWorker` approach (main thread). pdfjs v6 supports importing `pdfjs-dist/build/pdf.mjs` with worker disabled by NOT setting workerSrc — it falls back to fake worker. Actually v6 falls back automatically when worker errors (the `try{...}catch{...}` in #Ia).
- The real likely break: the ?url import in Brave mobile may resolve with a hashed filename that fails MIME (Vite serves .mjs with JS MIME; production Cloudflare static serving of .mjs may return wrong MIME type causing module worker failure).
- Production serving: assets hashed; .mjs files get application/javascript MIME in production — should be fine. But the ?url import returns a URL like /assets/pdf.worker.min-HASH.mjs; Chromium module-worker requires correct MIME + same origin + CSP.
- Fix plan: (1) set workerSrc with explicit absolute URL; (2) wrap the whole worker setup in try/catch and fall back to disabling the worker (import pdf.mjs without workerSrc on failure — fake worker path); (3) add regression test coverage for inspectPdf/renderPdfPage contracts.
